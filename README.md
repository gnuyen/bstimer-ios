# bsTimer for iOS

bsTimer is an iOS app that runs csTimer from `https://cstimer.gnuyen.org` in a
`WKWebView` and gives it the Web Bluetooth support iOS Safari lacks.
`bluetooth-shim.js` provides `navigator.bluetooth` inside the page and forwards
every call to CoreBluetooth (`BluetoothBridge.swift`). csTimer itself is
unmodified apart from one small script on the server (see *Server setup*). See
[PROTOCOL.md](PROTOCOL.md) for the bridge contract.

bsTimer is an unofficial wrapper. csTimer is written by
[cs0x7f](https://github.com/cs0x7f/cstimer) and licensed under GPL-3.0; this repository
contains none of its code, only the app that loads it.

The app also keeps the screen awake while a timer is in inspection, ready or running,
and lets it auto-lock normally when the timer is idle.

## Website choice

The iOS Settings app (Settings > Apps > bsTimer) has a "Website" choice: bsTimer
(default, `https://cstimer.gnuyen.org`) or csTimer.net. The two sites keep separate
solves on the device. Bluetooth and the screen lock work on both. iCloud sync is
bsTimer only. Google sign-in does not work in the app on csTimer.net (its login
returns to csTimer.net in the system sign-in sheet); use WCA sign-in there. The
change takes effect when you return to the app.

## Branding

The app is called bsTimer (name, icon, messages) so it isn't mistaken for the official
csTimer. The icon is generated by `scripts/make-icon.swift` (run it on a Mac). The web
address stays `cstimer.gnuyen.org`, and internal identifiers (project and
folder names, the `cstimerBLE` bridge, the `cstimerbt://` sign-in callback) are unchanged.
The bundle id is `org.gnuyen.bstimer`.

## Server setup

Google sign-in runs in an `ASWebAuthenticationSession` and returns to the csTimer page
with the token in the URL fragment. To get it back into the app, copy
`server/app-auth.js` to the server's `js/` folder and load it first in `index.php`'s
`<head>`:

```html
<script src="js/app-auth.js"></script>
```

It only acts when the URL carries `state=cstimer-ios`, which only the app adds, so
browsers and the home-screen web app are unaffected. WCA sign-in needs nothing extra.

For offline use, replace csTimer's placeholder `sw.js` at the site root with
`server/sw.js`. csTimer already registers it. After one online launch the page and its
scripts are cached, so the app (and the home-screen web app) opens without a
connection. The page is fetched fresh when online; scripts are refreshed in the
background, so a deploy shows up on the second launch. The app lists the site under
`WKAppBoundDomains`, which WKWebView requires before it runs service workers.

## Build and run (on a Mac)

1. Install Xcode and XcodeGen: `brew install xcodegen`
2. `xcodegen generate` in this directory, then open `CstimerBT.xcodeproj`.
3. Signing: create `Config/Local.xcconfig` containing `DEVELOPMENT_TEAM = <your Team ID>` (see `Config/Signing.xcconfig`; git ignores it), then run `xcodegen generate` again. Or pick a team in Xcode under *Signing & Capabilities*, which `xcodegen generate` resets. The bundle id is `org.gnuyen.bstimer`; if your team can't register it, change `PRODUCT_BUNDLE_IDENTIFIER` in `project.yml`.
4. On the iPhone enable *Settings → Privacy & Security → Developer Mode*, connect
   it, pick it as the run destination and press Run. The first launch may require
   trusting the developer under *Settings → General → VPN & Device Management*.

Run `xcodegen generate` after pulling. It creates `Info.plist` and
`bsTimer.entitlements`, both of which git ignores.

## iCloud sync

In bsTimer mode the page syncs to the user's private CloudKit database (container
`iCloud.org.gnuyen.bstimer`, one record named `snapshot` of type `Snapshot` holding
zlib-compressed JSON in an asset) with no sign-in, and keeps a copy on the bsTimer
sync server. That server's sync code is stored in iCloud key-value storage (key
`serverCode`) so other devices and reinstalls reuse it. The bridge is
`CloudBridge.swift` (message handler `bsCloud`, see [PROTOCOL.md](PROTOCOL.md)).

Setup for a new developer team:

1. `project.yml` already requests the iCloud entitlements (CloudKit container and
   key-value storage).
2. In Xcode, open Signing & Capabilities for the target; under iCloud make sure the
   container `iCloud.org.gnuyen.bstimer` is ticked (press + to create it if Xcode says
   it doesn't exist; use your own container id if you change the bundle id, and update
   `CloudBridge.containerIdentifier` and `project.yml`).
3. Debug builds use CloudKit's Development environment, where the record type is
   created on the first save. Before a TestFlight or App Store build, open the CloudKit
   Console, pick the container, and "Deploy Schema Changes" to Production.
4. The simulator needs an iCloud account signed in (Settings app) to test sync; without
   one the page falls back to the website's sync options.

## Debugging

Debug builds set `isInspectable`, so on the Mac *Safari → Develop → (iPhone) →
cstimer.gnuyen.org* opens Web Inspector for the page. Native logs show in Xcode's
console.
